## Issue #1: Form Validation Error

### Problem
```
** (FunctionClauseError) no function clause matching in 
OllamaChatWeb.ChatLive.handle_event/3
    handle_event("validate", %{"_target" => ["message"]}, ...)
```

**Severity**: CRITICAL - Prevented all text input when MCP was enabled  
**User Impact**: Application unusable with MCP features

### Root Cause
Phoenix LiveView changes form payload serialization format when socket assigns are large (MCP tool metadata is ~15KB). Instead of:
```elixir
%{"message" => "user input"}
```
It sends:
```elixir
%{"_target" => ["message"], "value" => "user input"}
```

The original `handle_event/3` only matched the first format.

### Solution
Added second function clause to handle both payload formats:

```elixir
# Handles standard format
@impl true
def handle_event("validate", %{"message" => message}, socket) 
    when is_binary(message) do
  {:noreply, assign(socket, :form, to_form(%{"message" => message}))}
end

# Handles alternate format with _target
@impl true
def handle_event("validate", %{"_target" => ["message"]} = params, socket) do
  message = params["value"] || ""
  {:noreply, assign(socket, :form, to_form(%{"message" => message}))}
end
```

## Issue #2: Tool Result Handling Error

### Problem
```
** (FunctionClauseError) no function clause matching in 
OllamaChat.MCPPromptBuilder.build_tool_result_message/2
    build_tool_result_message("list_allowed_directories", %ExMCP.Response{...})
```

**Severity**: CRITICAL - All MCP tool executions crashed  
**User Impact**: MCP features completely broken

### Root Cause
The ExMCP library returns `%ExMCP.Response{}` structs, but our code expected plain lists. The function signature was:

```elixir
@spec build_tool_result_message(String.t(), list()) :: String.t()
```

But it received:
```elixir
%ExMCP.Response{
  content: [%{type: "text", text: "result..."}],
  ...
}
```

### Solution
Added pattern matching for ExMCP.Response struct:

```elixir
@spec build_tool_result_message(String.t(), list() | struct()) :: String.t()

# New clause - extracts content from struct
def build_tool_result_message(tool_name, %ExMCP.Response{content: content})
    when is_list(content) do
  build_tool_result_message(tool_name, content)
end

# Original clause - handles list
def build_tool_result_message(tool_name, result) when is_list(result) do
  # ... existing implementation
end
```

Also added support for both atom and string keys in content items:

```elixir
defp format_tool_result(result) when is_list(result) do
  Enum.map_join(result, "\n\n", fn
    # Atom keys (from ExMCP.Response)
    %{type: "text", text: text} -> text
    %{type: "image", data: _, mimeType: mime} -> "[Image: #{mime}]"
    
    # String keys (from plain maps)
    %{"type" => "text", "text" => text} -> text
    %{"type" => "image", "data" => _, "mimeType" => mime} -> "[Image: #{mime}]"
    
    other -> inspect(other)
  end)
end
```

## Issue #3: Dialyzer False Positives

### Problem
```
lib/ollama_chat/mcp_client.ex:196:15:pattern_match 
  The pattern can never match the type {:error, _} | {:ok, %{binary() => [map()]}}
  
lib/ollama_chat/mcp_client.ex:244:8:unused_fun 
  Function requires_approval?/2 will never be called
```

**Severity**: LOW - Dialyzer warnings, no runtime impact  
**User Impact**: None (development tool only)

### Root Cause
ExMCP library has incorrect typespecs. It declares:
```elixir
@spec list_tools(pid()) :: {:ok, map()} | {:error, term()}
```

But actually returns:
```elixir
{:ok, %ExMCP.Response{tools: [...]}}
```

Our code correctly handles the struct, but Dialyzer can't verify it against the incorrect typespec.

### Solution
Added targeted `@dialyzer` suppressions:

```elixir
@dialyzer {:nowarn_function, discover_all_tools: 1}
defp discover_all_tools(clients) do
  # ... implementation that pattern matches on ExMCP.Response
end

@dialyzer {:nowarn_function, requires_approval?: 2}
defp requires_approval?(server_config, tool_name) do
  # ... called from discover_all_tools (which is suppressed)
end
```

## Issue #4: Collapsible Tool Messages UX Improvement

### Problem
Tool execution messages (tool calls, results, and empty intermediate responses) were always displayed prominently in the chat, cluttering the interface and making it difficult to focus on the actual conversation.

**Severity**: LOW - UX improvement  
**User Impact**: Visual clutter, reduced readability

### Root Cause
- Tool call and result messages were displayed as full-width notification boxes
- Took up significant vertical space in chat
- No way to hide technical details when not needed
- Empty intermediate responses (whitespace only) shown as regular messages

### Solution
Implemented collapsible `<details>` elements for tool messages:

```elixir
<% message.role == "tool_call" or message.role == "tool_result" -> %>
  <details class="bg-slate-800/50 border border-slate-600 rounded-lg">
    <summary class="cursor-pointer hover:bg-slate-700/50 flex items-center gap-2">
      <.icon name="hero-chevron-right" class="details-chevron" />
      <%= if message.role == "tool_call" do %>
        Calling tool: {message.tool_name}
      <% else %>
        Tool completed: {message.tool_name}
      <% end %>
    </summary>
    <div class="px-4 py-3 border-t border-slate-600">
      <!-- Full tool arguments or results -->
    </div>
  </details>
```

Added helper function:
```elixir
defp empty_response?(content) when is_binary(content) do
  String.trim(content) == ""
end
```

Added CSS for chevron animation:
```css
details summary .details-chevron {
    transition: transform 0.2s ease;
}

details[open] summary .details-chevron {
    transform: rotate(90deg);
}
```

**Messages Now Collapsed**:
- Tool call messages (`role: "tool_call"`)
- Tool result messages (`role: "tool_result"`)  
- Empty intermediate assistant responses (whitespace only)

## Lessons Learned

### 1. External Library Integration
**Issue**: ExMCP library has incorrect typespecs  
**Lesson**: Always verify actual return types, don't trust specs blindly  
**Action**: Add defensive pattern matching for both expected formats

### 2. LiveView Payload Variations
**Issue**: Phoenix LiveView changes payload format with large assigns  
**Lesson**: Handle multiple payload formats for robustness  
**Action**: Add comprehensive pattern matching for form events

### 3. Struct vs Map Handling
**Issue**: Libraries may return structs instead of plain maps  
**Lesson**: Pattern match on both struct and map formats  
**Action**: Support both atom and string keys

### 4. Dialyzer Suppressions
**Issue**: False positives from external libraries  
**Lesson**: Use targeted suppressions with clear documentation  
**Action**: Add comments explaining why suppression is needed

### 5. Progressive Disclosure
**Issue**: Too much technical information always visible  
**Lesson**: Use collapsible elements for optional details  
**Action**: Native `<details>` elements for accessibility and simplicity
